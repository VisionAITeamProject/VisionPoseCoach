# Vision Pose Coach 프론트엔드 연동 가이드

> 목적: 프론트엔드 담당자가 **BLE, Wi‑Fi, MJPG, WebSocket을 각각 왜 쓰는지** 이해하고, 앱에서 어떤 순서로 무엇을 구현해야 하는지 알 수 있게 정리한 문서입니다.

---

## 1. 한 줄 요약

Vision Pose Coach의 프론트엔드는 Raspberry Pi와 네 가지 통신 방식을 사용합니다.

| 기술 | 프론트에서 쓰는 시점 | 역할 | 데이터 성격 |
|---|---|---|---|
| BLE Bluetooth | 최초 기기 등록 / Wi‑Fi 설정 | Raspberry Pi에게 Wi‑Fi SSID/password 전달 | 작은 JSON |
| Wi‑Fi | BLE 설정 완료 이후 | 앱과 Raspberry Pi 서버가 통신하는 네트워크 경로 | HTTP/WebSocket/MJPG의 기반 |
| MJPG | 카메라 미리보기 화면 | Raspberry Pi 카메라 영상을 프론트에 보여줌 | JPEG 프레임 스트림 |
| WebSocket | 측정 시작/중지/실시간 상태 | 측정 상태, 자세/졸음 결과, 화면 상태를 실시간 수신 | JSON 이벤트 |

핵심은 **BLE는 처음 Wi‑Fi를 잡아주는 용도**이고, 실제 서비스 사용 중에는 **Wi‑Fi 기반 HTTP, WebSocket, MJPG**를 사용한다는 점입니다.

---

## 2. 전체 제품 흐름

```text
[최초 세팅]
프론트 앱
  ↓ BLE scan
Raspberry Pi: VisionPoseCoach-Pi 발견
  ↓ BLE connect
Wi‑Fi SSID/password를 BLE GATT write
  ↓
Raspberry Pi가 nmcli로 Wi‑Fi 연결
  ↓
BLE status에서 WIFI_CONNECTED 확인
  ↓
BLE disconnect

[서비스 사용]
프론트 앱
  ↓ Wi‑Fi 기반 HTTP
/health, /network/status로 기기 상태 확인
  ↓
/mjpg로 카메라 프리뷰 표시
  ↓
/ws WebSocket 연결
  ↓
start_session 명령 전송
  ↓
status / measurement 이벤트 수신
  ↓
stop_session 또는 시간 종료
  ↓
/session/latest-report 또는 /session/report/{session_id}로 결과 조회
```

프론트에서 가장 중요하게 이해해야 할 점은, **BLE 연결과 WebSocket 연결은 같은 통신이 아니다**라는 것입니다.

```text
BLE
→ Wi‑Fi 정보를 넘기는 초기 설정 통로

WebSocket
→ Wi‑Fi 연결 이후 측정 상태와 실시간 결과를 주고받는 통로

MJPG
→ Wi‑Fi 연결 이후 카메라 화면만 보여주는 영상 스트림
```

---

## 3. 프론트가 구현해야 하는 화면 흐름

프론트 화면은 크게 세 덩어리로 나누는 것이 좋습니다.

### 3.1 기기 등록 / Wi‑Fi 설정 화면

사용자가 처음 제품을 연결할 때 필요한 화면입니다.

프론트가 해야 할 일:

```text
1. Bluetooth 권한 요청
2. BLE scan 시작
3. VisionPoseCoach-Pi 기기 찾기
4. BLE connect
5. GATT service discover
6. Hello / Device Info characteristic read
7. Wi‑Fi SSID/password 입력 UI 표시
8. Wi‑Fi Configure characteristic에 JSON write
9. Status characteristic read 또는 notify로 결과 확인
10. WIFI_CONNECTED면 BLE disconnect
11. 이후 Wi‑Fi 기반 /health 또는 /network/status 확인
```

화면 상태 예시:

```text
BLUETOOTH_PERMISSION_REQUIRED
SCANNING_DEVICE
DEVICE_FOUND
CONNECTING_BLE
BLE_CONNECTED
WIFI_INPUT
CONFIGURING_WIFI
WIFI_CONNECTED
FAILED
```

### 3.2 기기 상태 / 측정 준비 화면

Wi‑Fi 연결 이후에는 Raspberry Pi FastAPI 서버에 접근합니다.

프론트가 해야 할 일:

```text
1. GET /health 호출
2. device_ready, network_ready, camera_ready 확인
3. camera_ready가 true면 카메라 프리뷰 /mjpg 표시 가능
4. WebSocket /ws 연결
5. 서버가 보내는 session_snapshot 수신
6. screen_hint에 따라 화면 이동
```

### 3.3 측정 화면

측정 화면에서는 **MJPG와 WebSocket을 동시에 사용**합니다.

```text
MJPG
→ 화면에 카메라 영상 표시

WebSocket
→ 측정 상태, 남은 시간, 자세/졸음 결과 수신
```

프론트가 해야 할 일:

```text
1. /mjpg 스트림을 이미지/비디오 영역에 표시
2. /ws 연결 유지
3. 측정 시작 버튼 클릭 시 start_session 전송
4. status 이벤트로 준비/캘리브레이션/카운트다운 표시
5. measurement 이벤트로 자세/졸음 결과 표시
6. stop_session 또는 측정 완료 시 결과 화면 이동
```

# 4. BLE Bluetooth 연동

## 4.1 BLE가 무엇이고 왜 쓰는가

BLE는 Bluetooth Low Energy의 약자입니다. 일반 블루투스보다 저전력이고, 작은 데이터를 주고받는 데 적합합니다.

우리 프로젝트에서 BLE를 쓰는 이유는 간단합니다.

Raspberry Pi가 아직 Wi‑Fi에 연결되지 않은 상태에서는 프론트 앱이 HTTP/WebSocket으로 Raspberry Pi에 접근할 수 없습니다. 그래서 처음 한 번은 가까운 거리에서 BLE로 Raspberry Pi를 찾고, 앱이 사용자의 Wi‑Fi 정보를 Raspberry Pi에 전달해야 합니다.

```text
왜 BLE가 필요한가?

Raspberry Pi가 Wi‑Fi 연결 전이다
→ 앱이 HTTP로 접근할 수 없다
→ BLE로 기기를 찾는다
→ BLE로 Wi‑Fi 정보를 넘긴다
→ Raspberry Pi가 Wi‑Fi에 연결된다
→ 이후부터는 HTTP/WebSocket/MJPG 사용
```

BLE는 **측정 데이터 전송용이 아닙니다.** 카메라 영상이나 자세 측정값을 BLE로 보내면 안 됩니다. 그건 느리고 구조도 복잡해집니다.

---

## 4.2 현재 서버 BLE 구현 상태

현재 서버 쪽에는 실제 BLE GATT 서버 코드가 있습니다.

| 항목 | 상태 |
|---|---|
| 실제 BLE GATT 서버 코드 | 있음 |
| 파일 | `network/ble_gatt_server.py` |
| 실행 스크립트 | `tools/run_ble_gatt_server.py` |
| Device Name (연결 후 확인) | `VisionPoseCoach-Pi` |
| Advertisement LocalName | 기본 `VPC-Pi`, 환경에 따라 표시되지 않을 수 있음 |
| Advertising backend | `auto` / `dbus` / `btmgmt` (프론트 GATT 계약에는 영향 없음) |
| BLE 용도 | 초기 Wi‑Fi 설정 |
| 실제 Pi 검증 | 아직 필요 |

주의할 점:

`/provisioning/ble/*` API는 실제 BLE가 아닙니다. 이 API는 개발 중 HTTP로 BLE 흐름을 흉내 내는 mock/debug API입니다.

```text
실제 BLE
→ network/ble_gatt_server.py
→ tools/run_ble_gatt_server.py

HTTP mock/debug
→ /provisioning/ble/*
```

프론트 앱은 실제 제품 흐름에서는 `/provisioning/ble/*`를 쓰는 것이 아니라, **BLE GATT characteristic을 read/write**해야 합니다.

---

## 4.3 BLE GATT 스펙

프론트 팀은 아래 값을 그대로 사용하면 됩니다.

```text
Device Name:
VisionPoseCoach-Pi

Advertisement LocalName:
VPC-Pi (BlueZ fallback 시 생략될 수 있음)

Service UUID:
9f4c0001-7d9a-4b57-9d9f-000000000001

Wi‑Fi Configure Characteristic UUID:
9f4c0002-7d9a-4b57-9d9f-000000000002

Status Characteristic UUID:
9f4c0003-7d9a-4b57-9d9f-000000000003

Hello / Device Info Characteristic UUID:
9f4c0004-7d9a-4b57-9d9f-000000000004
```

Characteristic 역할은 다음과 같습니다.

| Characteristic | 권한 | 프론트 사용법 |
|---|---|---|
| Hello / Device Info | Read only | 이 기기가 VisionPoseCoach 기기인지 확인 |
| Wi‑Fi Configure | Write | SSID/password JSON 전송 |
| Status | Read / Notify | Wi‑Fi 설정 진행 상태 확인 |

---

## 4.4 BLE 연결 순서

프론트 구현 순서는 다음과 같습니다.

```text
1. BLE scan 시작
2. Service UUID가 일치하는 기기를 우선 찾기
   광고 이름 VPC-Pi는 보조 정보로만 사용하며 환경에 따라 안 보일 수 있음
3. BLE connect
4. GATT service discover
5. Hello / Device Info characteristic read
6. Status characteristic notify 구독 또는 read
7. 사용자가 Wi‑Fi SSID/password 입력
8. Wi‑Fi Configure characteristic에 JSON write
9. Status가 WIFI_CONFIGURING → WIFI_CONNECTED 또는 FAILED로 바뀌는지 확인
10. WIFI_CONNECTED면 BLE disconnect
11. 이후 Wi‑Fi 기반 HTTP/WebSocket/MJPG로 전환
```

연결 전 스캔 결과의 이름만으로 기기를 최종 확정하지 않습니다. 연결 후 `Hello / Device Info`를 read하여 응답의 `device_name`이 `VisionPoseCoach-Pi`이고 `service_uuid`가 일치하는지 최종 확인합니다.

프론트에서 `Hello / Device Info`에 JSON을 write하지 않습니다. 이 characteristic은 read only입니다.

Hello read 응답 예시:

```json
{
  "type": "device_info",
  "device_name": "VisionPoseCoach-Pi",
  "service_uuid": "9f4c0001-7d9a-4b57-9d9f-000000000001"
}
```

---

## 4.5 Wi‑Fi 설정 payload

프론트가 BLE write로 보내야 하는 JSON입니다.

```json
{
  "type": "configure_wifi",
  "client_id": "phone-001",
  "ssid": "MyWifi",
  "password": "my-password"
}
```

전송 규칙:

```text
- UTF‑8 JSON으로 인코딩
- Wi‑Fi Configure Characteristic에 write
- 가능하면 write with response 사용
- 현재 서버는 512 bytes 이하 단일 JSON write 기준
- type은 반드시 configure_wifi
- ssid는 필수
- password는 일반적인 WPA/WPA2 Wi‑Fi에서 필수
```

보안 주의:

```text
- password를 로그에 찍지 않기
- 디버그 콘솔에 payload 전체 출력하지 않기
- 에러 화면에 password 표시하지 않기
- status 화면에 password 표시하지 않기
```

---

## 4.6 BLE Status 응답

Status characteristic read/notify 응답 예시입니다.

```json
{
  "mode": "real_ble",
  "device_name": "VisionPoseCoach-Pi",
  "state": "WIFI_CONNECTED",
  "wifi_connected": true,
  "ssid": "MyWifi",
  "last_error": null
}
```

가능한 state 값:

```text
IDLE
ADVERTISING
CONNECTED
WIFI_CONFIGURING
WIFI_CONNECTED
FAILED
```

프론트에서 가장 중요하게 처리해야 할 상태는 이 세 가지입니다.

| state | 의미 | 프론트 처리 |
|---|---|---|
| WIFI_CONFIGURING | Raspberry Pi가 Wi‑Fi 연결 시도 중 | 로딩 표시 |
| WIFI_CONNECTED | Wi‑Fi 연결 성공 | BLE 끊고 HTTP 확인으로 전환 |
| FAILED | Wi‑Fi 연결 실패 | 비밀번호 재입력/재시도 안내 |

`CONNECTED` 상태는 실제 스마트폰 연결 이벤트를 100% 정확히 의미한다기보다 provisioning 흐름상 연결 단계에 가까울 수 있습니다. 프론트는 `WIFI_CONFIGURING`, `WIFI_CONNECTED`, `FAILED` 중심으로 처리하는 것이 안전합니다.

---

## 4.7 BLE 이후 IP 확인 문제

BLE로 Wi‑Fi 연결이 성공해도 프론트가 바로 `/health`를 호출하려면 Raspberry Pi의 IP 주소를 알아야 합니다.

현재 BLE status payload에는 기본적으로 `local_ip`가 포함되어 있지 않습니다. 따라서 프론트/서버 팀이 실제 통합 전 아래 중 하나를 정해야 합니다.

| 방법 | 설명 | 추천도 |
|---|---|---|
| BLE status에 local_ip 추가 | Wi‑Fi 연결 성공 후 BLE status에 Raspberry Pi IP를 포함 | 가장 직관적 |
| mDNS/hostname 사용 | `raspberrypi.local` 같은 주소로 접근 | 네트워크 환경에 따라 실패 가능 |
| 클라우드 서버 등록 | Pi가 Spring 서버에 자신의 online 상태/IP를 등록 | 제품화에 유리 |
| 사용자가 IP 직접 입력 | 개발/테스트용 | 제품 UX로는 부적합 |

프론트 연동을 쉽게 하려면 서버 쪽에서 `WIFI_CONNECTED` status에 `local_ip`를 추가하는 개선을 고려하는 것이 좋습니다.

예상 개선 응답:

```json
{
  "mode": "real_ble",
  "device_name": "VisionPoseCoach-Pi",
  "state": "WIFI_CONNECTED",
  "wifi_connected": true,
  "ssid": "MyWifi",
  "local_ip": "192.168.0.23",
  "last_error": null
}
```

# 5. Wi‑Fi 연동

## 5.1 Wi‑Fi가 무엇이고 왜 필요한가

Wi‑Fi는 BLE 이후 실제 서비스 통신에 사용되는 네트워크입니다.

BLE는 작은 설정 데이터만 보내기 위한 통로이고, 카메라 영상, 실시간 측정 결과, 세션 제어 같은 기능은 모두 Wi‑Fi 기반으로 동작합니다.

```text
Wi‑Fi 연결 이후 사용하는 것

- HTTP API
- WebSocket
- MJPG camera stream
```

---

## 5.2 서버 Wi‑Fi 모드

Raspberry Pi 서버의 `WiFiManager`는 세 가지 모드가 있습니다.

| 모드 | 의미 | 프론트 관점 |
|---|---|---|
| dry_run | 실제 Wi‑Fi 연결 안 함 | 안전한 기본값, 개발용 |
| mock | 가짜 Wi‑Fi 목록/성공 응답 | UI 개발/테스트용 |
| real | 실제 `nmcli`로 Wi‑Fi 연결 | Raspberry Pi 실기기용 |

서버 실행 예시:

```bash
VPC_WIFI_MODE=mock python server_main.py
VPC_WIFI_MODE=real python server_main.py
```

실제 제품에서는 `real` 모드가 필요합니다.

---

## 5.3 프론트가 호출할 수 있는 네트워크 API

Base URL은 실제 Raspberry Pi IP 기준입니다.

```text
http://<PI_IP>:8000
```

주요 API:

| Method | Endpoint | 용도 |
|---|---|---|
| GET | `/health` | 앱 시작 시 기기 전체 상태 확인 |
| GET | `/network/status` | Wi‑Fi 연결 상태 확인 |
| GET | `/network/wifi/scan` | 주변 Wi‑Fi 목록 조회 |
| POST | `/network/wifi/configure` | HTTP로 Wi‑Fi 설정 |
| POST | `/network/wifi/forget` | 저장된 Wi‑Fi 상태 초기화 |

중요:

실제 제품의 최초 Wi‑Fi 설정은 HTTP `/network/wifi/configure`보다 BLE를 사용하는 것이 맞습니다. Raspberry Pi가 Wi‑Fi에 연결되기 전에는 프론트가 HTTP로 Pi에 접근할 수 없기 때문입니다.

`/network/wifi/configure`는 다음 상황에서 유용합니다.

```text
- 개발 중 mock 테스트
- Pi와 앱이 이미 같은 네트워크에 있는 경우
- 관리자/디버그 화면
```

---

## 5.4 /health 응답에서 봐야 할 값

프론트는 앱 시작 또는 Wi‑Fi 연결 후 `/health`를 호출해서 기기가 준비됐는지 확인합니다.

예상 응답 구조:

```json
{
  "type": "health",
  "ok": true,
  "app": {
    "server_ready": true,
    "device_ready": true,
    "network_ready": true,
    "wifi_connected": true,
    "provisioning_required": false,
    "camera_ready": true,
    "session_running": false,
    "state": "IDLE",
    "screen_hint": "HOME",
    "message": "기기 준비됨"
  }
}
```

프론트가 우선적으로 볼 값:

| 필드 | 의미 | 프론트 처리 |
|---|---|---|
| `app.network_ready` | 네트워크 준비 여부 | false면 BLE/Wi‑Fi 설정 유도 |
| `app.wifi_connected` | Wi‑Fi 연결 여부 | false면 provisioning 필요 |
| `app.provisioning_required` | 설정 필요 여부 | true면 기기 등록 화면 이동 |
| `app.camera_ready` | 카메라 사용 가능 여부 | false면 카메라 오류 안내 |
| `app.session_running` | 측정 진행 중 여부 | true면 측정 화면 복구 |
| `app.screen_hint` | 추천 화면 | HOME/PREPARE/MEASUREMENT/RESULT/ERROR |

# 6. MJPG 카메라 스트림

## 6.1 MJPG가 무엇인가

MJPG는 Motion JPEG 방식입니다. 서버가 JPEG 이미지를 계속 이어서 보내고, 프론트는 그것을 영상처럼 보여줍니다.

일반 JSON API와 다르게 응답이 끝나지 않습니다. 계속 프레임을 흘려보내는 스트림입니다.

```text
HTTP GET /mjpg
→ JPEG frame
→ JPEG frame
→ JPEG frame
→ ... 계속 전송
```

우리 프로젝트에서 MJPG는 **카메라 프리뷰 전용**입니다.

```text
MJPG가 하는 일
→ Raspberry Pi 카메라 화면 보여주기

MJPG가 하지 않는 일
→ 측정 시작/중지
→ 자세/졸음 결과 JSON 전달
→ 세션 상태 전달
```

측정 상태와 결과는 WebSocket으로 받아야 합니다.

---

## 6.2 MJPG endpoint

```text
GET http://<PI_IP>:8000/mjpg
```

응답 타입:

```text
multipart/x-mixed-replace; boundary=frame
```

프론트 처리 방식:

| 플랫폼 | 처리 방식 |
|---|---|
| Web | `<img src="http://<PI_IP>:8000/mjpg">` 방식 가능 |
| Flutter/App | MJPG 지원 패키지 또는 스트림 파서 필요 |
| Android native | ImageView에 직접 넣기 어렵고 MJPG parser 필요 |
| iOS native | URLSession stream 처리 또는 라이브러리 필요 |

프론트에서 주의할 점:

```text
- 일반 HTTP JSON client로 호출하면 안 됨
- 응답이 끝나지 않는 스트림임
- 화면을 벗어나면 stream 연결을 정리해야 함
- 앱이 백그라운드로 가면 stream 정리 권장
- 실패 시 재시도 버튼 또는 자동 재연결 처리 필요
```

---

## 6.3 MJPG와 WebSocket을 같이 쓰는 이유

측정 화면에서는 보통 두 연결을 동시에 엽니다.

```text
/mjpg
→ 카메라 영상 표시

/ws
→ 측정 상태와 결과 JSON 수신
```

이렇게 나누는 이유는 데이터 성격이 다르기 때문입니다.

| 데이터 | 적합한 통신 |
|---|---|
| 카메라 프레임 | MJPG |
| 측정 시작/중지 명령 | WebSocket |
| 자세 라벨 | WebSocket |
| 졸음 상태 | WebSocket |
| 남은 시간 | WebSocket |
| 화면 상태 | WebSocket |

---

# 7. WebSocket 실시간 측정 연동

## 7.1 WebSocket이 무엇이고 왜 쓰는가

WebSocket은 한 번 연결해두면 서버와 프론트가 계속 양방향으로 JSON 메시지를 주고받을 수 있는 통신입니다.

일반 HTTP는 요청할 때마다 응답을 받는 구조입니다.

```text
HTTP
앱: 상태 주세요
서버: 여기 있어요
앱: 다시 상태 주세요
서버: 여기 있어요
```

WebSocket은 연결을 유지하고 서버가 필요할 때 바로 보낼 수 있습니다.

```text
WebSocket
앱: 연결할게요
서버: 현재 상태입니다
서버: 1초 후 측정 결과입니다
서버: 1초 후 측정 결과입니다
서버: 측정 완료입니다
```

우리 프로젝트에서는 WebSocket을 다음 용도로 씁니다.

```text
- 측정 시작 명령
- 측정 중지 명령
- 준비/캘리브레이션/카운트다운 상태 수신
- 측정 중 자세/졸음 결과 수신
- 남은 시간 수신
- 화면 이동 힌트 수신
```

---

## 7.2 WebSocket endpoint

```text
ws://<PI_IP>:8000/ws
```

보안 HTTPS/WSS 환경이 붙으면 나중에는 아래처럼 바뀔 수 있습니다.

```text
wss://<DOMAIN>/ws
```

현재 Raspberry Pi 로컬 개발 기준은 `ws://`입니다.

---

## 7.3 WebSocket 연결 직후

프론트가 `/ws`에 연결하면 서버는 현재 세션 상태를 `session_snapshot`으로 보냅니다.

예시:

```json
{
  "type": "session_snapshot",
  "session_id": null,
  "is_running": false,
  "state": "IDLE",
  "message": "측정 대기 중입니다.",
  "screen_hint": "HOME",
  "stage_remain_sec": null,
  "elapsed_sec": 0,
  "duration_sec": null,
  "remain_sec": null,
  "stop_reason": null,
  "latest_result": null
}
```

프론트는 연결 직후 이 payload를 보고 현재 화면을 복구할 수 있습니다.

---

## 7.4 프론트가 보내는 명령

### 측정 시작

```json
{
  "action": "start_session",
  "duration_sec": 1800
}
```

`duration_sec` 제한:

```text
최소: 300초
최대: 7200초
기본: 1800초
```

### 측정 중지

```json
{
  "action": "stop_session"
}
```

잘못된 명령을 보내면 서버는 error payload를 보냅니다.

---

## 7.5 서버가 보내는 status 이벤트

측정 흐름 상태는 `status` 이벤트로 옵니다.

예시:

```json
{
  "type": "status",
  "session_id": "20260713-xxxx",
  "is_running": true,
  "state": "CALIBRATING",
  "message": "캘리브레이션 중입니다.",
  "screen_hint": "PREPARE",
  "stage_remain_sec": 3,
  "elapsed_sec": 0,
  "duration_sec": 1800,
  "remain_sec": 1800,
  "stop_reason": null
}
```

가능한 state:

```text
IDLE
PREPARE_POSTURE
WAITING_5S
CALIBRATING
INITIAL_MEASURING_30S
COUNTDOWN_3S
MEASURING
STOPPED
ERROR
```

프론트는 `state`를 직접 처리해도 되고, 더 단순하게는 `screen_hint`를 기준으로 화면을 이동시켜도 됩니다.

screen_hint 매핑:

| screen_hint | 의미 | 추천 화면 |
|---|---|---|
| HOME | 대기 상태 | 홈/시작 화면 |
| PREPARE | 준비/캘리브레이션/카운트다운 | 측정 준비 화면 |
| MEASUREMENT | 측정 중 | 실시간 측정 화면 |
| RESULT | 측정 종료 | 결과 화면 |
| ERROR | 오류 | 오류 안내 화면 |

---

## 7.6 서버가 보내는 measurement 이벤트

측정 중에는 약 1초 단위로 measurement 이벤트가 옵니다.

예시:

```json
{
  "type": "measurement",
  "session_id": "20260713-xxxx",
  "is_running": true,
  "state": "MEASURING",
  "screen_hint": "MEASUREMENT",
  "elapsed_sec": 25,
  "duration_sec": 1800,
  "remain_sec": 1775,
  "posture_label": "Forward Head",
  "posture_confidence": 0.86,
  "fatigue_label": "Normal",
  "fatigue_probability": 0.12,
  "pose_detected": true,
  "face_detected": true,
  "error": null
}
```

프론트에서 표시하면 좋은 값:

| 필드 | 화면 표시 예시 |
|---|---|
| `elapsed_sec` | 측정 경과 시간 |
| `remain_sec` | 남은 시간 |
| `posture_label` | 현재 자세 상태 |
| `posture_confidence` | 자세 신뢰도 |
| `fatigue_label` | 졸음/피로 상태 |
| `fatigue_probability` | 졸음 확률 |
| `pose_detected` | 사람 자세 인식 여부 |
| `face_detected` | 얼굴 인식 여부 |
| `error` | 추론 오류 메시지 |

---

## 7.7 error 이벤트

예시:

```json
{
  "type": "error",
  "code": "INVALID_DURATION",
  "message": "측정 시간이 올바르지 않습니다.",
  "state": "IDLE",
  "screen_hint": "HOME"
}
```

프론트 처리:

```text
- message를 사용자에게 보여줌
- code에 따라 재시도/입력 수정/홈 이동 처리
- screen_hint가 있으면 해당 화면으로 복구 가능
```

# 9. 프론트 구현 우선순위

프론트 팀은 아래 순서로 붙이는 것이 좋습니다.

## 1단계: Wi‑Fi 연결 이후 기본 HTTP 확인

```text
1. 사용자가 Pi IP를 알고 있다고 가정
2. GET /health 호출
3. device_ready/network_ready/camera_ready 표시
4. GET /session/status 호출
```

이 단계는 BLE 없이도 가능합니다.

## 2단계: MJPG 프리뷰

```text
1. /mjpg 스트림 화면에 표시
2. 화면 이탈 시 stream 정리
3. 연결 실패/재시도 처리
```

## 3단계: WebSocket 측정 흐름

```text
1. /ws 연결
2. session_snapshot 수신
3. start_session 전송
4. status 이벤트 처리
5. measurement 이벤트 처리
6. stop_session 전송
7. 종료 후 결과 화면 이동
```

## 4단계: BLE Wi‑Fi provisioning

```text
1. Bluetooth 권한 처리
2. VisionPoseCoach-Pi scan
3. connect/discover/read/write/notify
4. configure_wifi payload write
5. WIFI_CONNECTED 확인
6. Pi IP 확인 방식 결정
7. /health 호출로 Wi‑Fi 통신 확인
```

BLE는 중요하지만 실제 기기 환경 의존성이 크기 때문에, 프론트 UI 개발은 `mock` 상태와 HTTP 상태 확인부터 진행하고, 이후 실제 Pi에서 BLE 통합 테스트하는 방식이 좋습니다.

# 10. 프론트에서 헷갈리면 안 되는 점

## 10.1 BLE와 Wi‑Fi는 같은 연결이 아니다

```text
BLE 연결 성공
→ 아직 HTTP/WebSocket 가능하다는 뜻이 아님

Wi‑Fi 연결 성공
→ 이후 HTTP/WebSocket/MJPG 가능
```

## 10.2 MJPG는 JSON API가 아니다

```text
/mjpg는 끝나지 않는 이미지 스트림
일반 HTTP JSON 요청처럼 처리하면 안 됨
```

## 10.3 WebSocket은 영상이 아니다

```text
/ws는 측정 상태와 결과 JSON용
카메라 영상은 /mjpg로 표시
```

## 10.4 /provisioning/ble/*는 실제 BLE가 아니다

```text
/provisioning/ble/*
→ HTTP mock/debug

실제 BLE
→ GATT characteristic read/write
```

## 10.5 Wi‑Fi 연결 후 Pi IP 확인 방식이 필요하다

프론트는 `http://<PI_IP>:8000`으로 접근해야 합니다. 따라서 실제 제품에서는 Pi IP를 어떻게 알릴지 결정해야 합니다.

추천 개선:

```text
BLE WIFI_CONNECTED status에 local_ip 포함
```

# 12. 실제 통합 테스트 체크리스트

## 12.1 Raspberry Pi 쪽

```bash
sudo systemctl status bluetooth
bluetoothctl show
rfkill list
nmcli device status
python -c "import dbus_next; print('dbus-next ok')"
```

BLE 서버 실행:

```bash
sudo -E env VPC_WIFI_MODE=mock \
  /home/willtek/VisionPoseCoach/.venv/bin/python \
  tools/run_ble_gatt_server.py \
  --debug \
  --device-name VisionPoseCoach-Pi \
  --advertise-name VPC-Pi \
  --advertising-backend auto \
  --advertising-instance 1

sudo -E env VPC_WIFI_MODE=real \
  /home/willtek/VisionPoseCoach/.venv/bin/python \
  tools/run_ble_gatt_server.py \
  --debug \
  --advertising-backend auto
```

`auto`는 D-Bus 광고를 먼저 시도하고 BlueZ가 `org.bluez.Error.Failed`를 반환하면 같은 adapter에서 `btmgmt` 광고로 전환합니다. `btmgmt`를 명시하려면 `--advertising-backend btmgmt`를 사용합니다. `btmgmt` 광고는 128-bit Service UUID를 안정적으로 싣기 위해 LocalName을 생략하므로 프론트는 반드시 Service UUID로 스캔해야 합니다. 어느 backend를 선택해도 GATT Application과 characteristic은 기존 D-Bus 구현을 그대로 사용하므로 프론트의 UUID와 payload 형식은 바뀌지 않습니다. 서버 종료 시 사용한 advertising instance는 자동 제거됩니다.

FastAPI 서버 실행:

```bash
VPC_WIFI_MODE=real python server_main.py
```

## 12.2 프론트 쪽

```text
1. BLE scan에서 Service UUID가 보이는지 (`VPC-Pi` 이름은 없을 수도 있음)
2. connect 성공하는지
3. service UUID discover 되는지
4. Hello characteristic read 되는지
5. Status characteristic read/notify 되는지
6. Wi‑Fi Configure characteristic write 성공하는지
7. status가 WIFI_CONNECTED 또는 FAILED로 바뀌는지
8. Wi‑Fi 연결 성공 후 /health 호출 가능한지
9. /mjpg 영상이 보이는지
10. /ws 연결 후 session_snapshot을 받는지
11. start_session 후 status/measurement가 오는지
```

`pytest` 통과는 Python 코드 계약만 확인합니다. 실제 advertisement 등록은 Raspberry Pi의 BlueZ/어댑터/펌웨어 조합에 따라 달라질 수 있으므로 Pi에서 위 scan/connect/Hello read 절차를 별도로 검증해야 합니다.

# 13. 현재 남은 결정 사항

현재 서버 코드는 프론트 연동을 위한 기반이 준비되어 있지만, 실제 제품 수준에서는 아래 사항을 결정해야 합니다.

## 13.1 Wi‑Fi 연결 후 Pi IP 전달 방식

현재 가장 큰 UX 이슈입니다.

프론트가 BLE로 Wi‑Fi 설정을 완료한 뒤, Pi의 HTTP 서버 주소를 알아야 합니다.

추천:

```text
BLE status payload에 local_ip 추가
```

또는 제품 구조상 Spring Boot 클라우드 서버를 사용한다면:

```text
Pi가 Spring 서버에 device online 상태와 접속 정보를 등록
앱은 Spring 서버에서 내 기기 상태 조회
```

## 13.2 BLE 서버와 FastAPI 서버 동시 실행 방식

현재 실제 BLE GATT 서버는 `tools/run_ble_gatt_server.py`로 별도 실행합니다. FastAPI는 `server_main.py`로 실행합니다.

제품화 시에는 다음 중 하나를 정해야 합니다.

```text
선택 A: systemd 서비스 2개로 분리 실행
- visionpose-api.service
- visionpose-ble.service

선택 B: 하나의 프로세스에서 같이 실행
- 구현은 편할 수 있지만 장애 분리 어려움
```

현재 구조에서는 선택 A가 더 안전합니다.

## 13.3 프론트 앱의 재연결 정책

프론트는 아래 상황을 처리해야 합니다.

```text
- WebSocket 끊김
- MJPG stream 실패
- BLE 연결 실패
- Wi‑Fi 비밀번호 오류
- Pi가 재부팅됨
- 앱이 백그라운드에서 돌아옴
```

권장:

```text
앱 resume 시 /health 재호출
WebSocket 끊기면 session/status로 복구 후 재연결
MJPG 실패 시 재시도 버튼 제공
BLE 실패 시 scan부터 다시 시작
```

# 14. 프론트 팀에게 설명할 때 사용할 말

팀원에게 짧게 설명할 때는 이렇게 말하면 됩니다.

```text
우리 프로젝트에서 블루투스는 측정 데이터를 보내는 용도가 아니라,
라즈베리파이가 처음 Wi‑Fi에 붙을 수 있도록 SSID와 비밀번호를 전달하는 초기 설정 통로입니다.

Wi‑Fi 연결이 끝나면 앱은 라즈베리파이 FastAPI 서버와 통신합니다.
카메라 영상은 /mjpg로 보고, 측정 시작/중지와 실시간 자세/졸음 결과는 /ws WebSocket으로 받습니다.

즉 프론트는 BLE provisioning 화면, MJPG 카메라 프리뷰, WebSocket 측정 상태 처리,
그리고 /health 기반 기기 상태 확인을 구현하면 됩니다.
```

# 15. 구현 완료 기준

프론트 연동 완료 기준은 다음입니다.

```text
1. 앱에서 VisionPoseCoach-Pi가 BLE scan으로 보인다.
2. 앱에서 BLE connect가 된다.
3. Hello characteristic을 read할 수 있다.
4. Wi‑Fi Configure characteristic에 SSID/password JSON을 write할 수 있다.
5. Status에서 WIFI_CONNECTED를 받을 수 있다.
6. 앱이 Pi의 /health를 호출할 수 있다.
7. 앱에서 /mjpg 카메라 프리뷰가 보인다.
8. 앱에서 /ws 연결 후 start_session을 보낼 수 있다.
9. 앱에서 status/measurement 이벤트를 화면에 반영한다.
10. 측정 종료 후 결과 화면으로 이동한다.
```

이 10개가 되면 BLE/Wi‑Fi/MJPG/WebSocket의 프론트 통합은 기본적으로 완료됐다고 볼 수 있습니다.
